# 独立目标跟踪：卡尔曼滤波与匈牙利匹配

2026-11-03 已接入实时摄像头程序。默认启动“检测+跟踪”，仍使用第二版 YOLO11n 权重，没有重新训练模型。

## 怎么启动和观察

双击项目根目录的 `启动USB识别.cmd`。

- 框上出现 `ID 1`、`ID 2` 等编号，颜色按 ID 固定。
- `ID 1?` 中的问号表示尚未达到确认命中次数，第二次命中后去掉问号。
- 小类名称、垃圾大类和置信度仍取自当前检测结果；跟踪模块不会伪改物品类别。
- 细线显示最近 15 次有效观测的中心轨迹。
- Q 退出，S 保存截图；截图和逐帧日志仍在 `outputs/live/`。

ID 是本次程序运行中的目标身份，不是类别编号。两个土豆应有两个不同 ID；同一个土豆缓慢移动时应保持原 ID。重启程序会重新编号。

临时切回纯检测：

```powershell
.\.venv\Scripts\python.exe scripts/run_live.py --no-tracking
```

## 实际实现

```text
YOLO predict 检测
    → 独立卡尔曼预测各条轨迹当前位置
    → 距离与尺寸门限排除不合理配对
    → 构建全部轨迹与检测框的代价矩阵
    → 独立匈牙利算法求全局匹配
    → 匹配成功：卡尔曼修正，沿用 ID
    → 未匹配检测：分配新 ID
    → 短时漏检轨迹：内部保留，超时删除
    → 显示 ID、平滑框和轨迹，写入日志
```

主要代码：

- `src/invc_vision/tracking.py`：卡尔曼滤波、匈牙利分配、轨迹生命周期。
- `src/invc_vision/app.py`：摄像头、检测、跟踪和日志接入。
- `src/invc_vision/overlay.py`：中文标签、稳定 ID 颜色、轨迹绘制。
- `tests/test_tracking.py`：匹配最优性与身份稳定性测试。

运行路径只调用 `model.predict()`，没有使用 `model.track()`、ByteTrack、BoT-SORT 或其他现成跟踪器。

### 卡尔曼滤波

每个目标有独立的 8 维状态：中心横纵坐标、框宽高及这四个量的变化率。采用恒速模型，以实际时间间隔更新转移矩阵和过程噪声。测量来自 YOLO 的检测框，使用 Joseph 形式更新协方差以减小数值误差。

摄像头使用采集时的单调时钟，视频文件使用媒体时间戳及帧率回退值。没有把每一帧硬当成固定 1/30 秒。

滤波器内部速度用于预测框的位置，不等于已完成项目要求的物理测速。目前日志的正式速度字段仍为空，后续再接入滑动窗口和标定。

### 匈牙利匹配

使用本项目实现的 Hungarian 原始/对偶增广算法，可处理矩形代价矩阵，没有将其他求解器当作匈牙利实现。

匹配代价结合：预测框 IoU（权重 0.55）、归一化中心距离（0.30）、类别不一致惩罚（0.15）。类别只是软惩罚，避免一次检测类别跳变立即重置 ID。

每条轨迹有单独的“未匹配”虚拟列；先尽可能保留合理匹配，再在这些匹配中最小化总代价。距离过远或宽高比例变化过大的配对被排除，不会为了完成一一分配强行匹配。

## 默认参数与行为

| 设置 | 默认值 |
|---|---|
| 检测置信度 / NMS IoU | 0.5 / 0.5 |
| 跨类别 NMS | 开启 |
| 短时漏检保留时间 | 1.0 秒 |
| 确认轨迹所需检测命中 | 2 次 |
| 相对距离门限系数 | 1.5 |
| 可视轨迹长度 | 最近 15 次观测 |

可通过 `--track-max-lost`、`--track-min-hits`、`--track-distance-factor` 调整，先用默认值验证实际画面。

未匹配预测只在内部用于短时恢复，不作为新的真实检测画在画面或发送。漏检期间目标可能暂时不显示，恢复后若关联成功仍沿用原 ID。超过保留时间的轨迹被删除，再出现时会得到新 ID；本阶段没有做遮挡后重识别。

### 第二版模型的 120 帧视频检查

目录：`outputs/tracking_validation_20261103/`。

使用一张有两个土豆真实标注的照片生成 120 帧受控平移视频，然后运行本机实际 YOLO 模型及完整跟踪程序。两个目标各保持同一个 ID，均 0 次 ID 切换、0 帧漏检。

- `annotated.mp4`：带 ID 和轨迹的视频。
- `preview.jpg`：最后一帧示例。
- `summary.json`：ID 稳定性统计。
- `detections.jsonl`：每帧完整检测与跟踪数据。
- `expected_motion.json`：生成视频时的已知目标位置。

这是从照片生成的视频检查，不代表已经在真实摄像头下完成双目标移动验收。视频中显示的处理 FPS 是离线处理速度，不能当成 USB 摄像头的实际采集速度。

### USB 摄像头检查

真实摄像头连续处理 90 帧，图像 1280×720，使用 RTX 5060 Ti；检查日志为 `outputs/live/tracking_usb_check_20261103.jsonl`，画面为同名 JPG。

本次测得中位处理速度约 9.9 FPS，中位跟踪计算约 0.29 ms。实际画面是近距离杂物，存在检测误报、目标出入及类别变化；该检查确认链路能运行，不能据此声称真实多目标跟踪已完全验收。

后续应把摄像头固定到木板视野，放两个分开的目标：先静止，再缓慢移动一个，最后同时缓慢移动，检查是否换号或串号。更复杂遮挡与外观完全相同物品的身份恢复不在本阶段已验证范围内。
